# 参考 Luma 的 GoMate 核心体验优化评估

调研日期：2026-11-05（Asia/Shanghai）。代码基准：`c96bf807`（调研时最新 `origin/main`）。本文区分 Luma 官方资料事实、GoMate 代码事实与尚未实施的建议。Luma 部分以官方帮助中心和公开页面为依据，未创建真实活动、提交报名或验证邮件投递；不把官方对流程的描述写成实际使用测试，也不据此声称转化率已经提高。

## 研究边界

GoMate 的已接受产品边界是“发现地点 → 创建或直接加入队伍 → 线下活动”，保留最小成员管理、时间地点、取消与完成；审批、站内聊天、收藏和复杂行动本已明确移出范围。优化建议须服从这一边界，不因 Luma 具有某项能力就恢复它。依据：[极简产品 ADR](adr/0001-minimal-location-team-product.md)。

## 结论：优先补齐三处连续性

**建议先让用户顺利完成第一次加入/发起，再让已加入的人清楚如何出发，最后补关键变更通知。** 优先级是基于代码和流程的判断，不是用户漏斗或留存数据。本文是研究记录，不是已接受的产品决策或实施规格；归档本文不代表批准上线下列功能。

| 顺序 | 核心问题                               | 最小改进                                                             | 预期收益与代价                                                           |
| ---- | -------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1    | 登录、注册、补资料会打断原任务         | 保留目标队伍、已选地点和创建输入，完成前置步骤后回到原任务           | 消除已确认的路径断点；沿用现有账户和权限规则，主要涉及跨页状态恢复       |
| 2    | 加入后已有状态，但赴约动作仍分散       | 在现有出发卡补齐明确状态、完整时间、集合说明、联系复制和单场日历入口 | 让用户知道是否确定出发、何时何地集合；以复用现有数据为主，日历需单独验证 |
| 3    | 活动信息变了，已加入的人需要主动回来看 | 先覆盖取消、成团和关键时间/集合信息变更的事务邮件                    | 降低成员按旧信息行动的风险；需持久投递、去重和失败处理，成本高于前两项   |

第一轮只建议做第 1 项和第 2 项中的页面内改善；日历单独交付，第 3 项待通知规则和可靠性设计明确后实施。无需同时扩建活动平台。

## 三项改进的具体边界

### 1. 让登录与补资料成为原任务的一部分

**具体场景：** 新用户收到队伍链接，想加入；或从地点详情点“发起队伍”。当前流程在注册和补微信号时会丢掉目标，迫使用户重新找队伍或地点。Luma 的可借鉴之处是报名围绕活动完成、已知信息不重复填写，而不是必须复制其匿名报名方式。

最小方案：

- 登录、注册、验证、补资料共用经过校验的同源返回目标；保留地点参数和语言。验证链接在新标签页打开时，也能回到发起操作的上下文；不要只假设原标签页仍存在。
- 缺微信号时先补这一项，并说明仅向同队成员展示；可采用轻量补填区，或现有资料页保存后返回。保留服务端当前要求，不顺带改变联系方式可见性。
- 离开创建页补资料前保存当前输入；失败后继续编辑，发布成功后清理恢复副本。浏览器存储不可用时给出可理解的降级；恢复时重新确认地点可用、日期仍在未来，不能自动发布。
- 登录完成后回到原队伍，仍由用户点击“加入”；重新核对满员、取消、已开始等状态，不自动报名。

创建页可以顺带将可选参与要求折叠，把默认时长及高级选项降为次要信息；标题、地点、时间、人数和简短说明仍清晰可见。先解决绕路和丢输入，不以随意减少必填项替代问题诊断。Luma 对初始输入与后续设置的区分见下方创建资料。

**验收：** 从同一地点发起、注册/验证或补资料后，仍回到该地点的创建页；填写内容不因补资料而丢失。两种语言及新标签页验证均覆盖；不接受站外回跳，也不把验证 token 放进 path/query 或草稿。加入失败/名额变化时保留原队伍上下文。

### 2. 在现有出发卡上补齐“我接下来做什么”

保留当前信息架构和持久已加入状态，避免另建一个“活动中心”。最小增量是：

- 时间同时给出星期、开始和预计结束时间，跨日明确结束日期；创建、详情和日历遵循同一地点时区语义，不让用户从“预计 3h”自行换算。
- 已加入但未成团时明确显示“已加入 · 等待队长确认出发”；已成团显示“已确认出发”。队长看到对应的“确认出发”动作及关闭招募的后果。只改善语义，暂不取消现有成团步骤或自动成团。
- 集合信息空缺时显示“集合信息待队长补充”，并给队长编辑入口；已有信息时增加复制。首层给成员一个明确的“联系队长/复制微信号”动作，复用现有私有数据；复制失败仍可手动选中文本。
- 后续增加单场“添加到日历”。第一版可只带活动标题、开始/结束、公开目的地和返回队伍的链接，集合点和微信继续在登录后的详情查看。待成团时明确标为暂定；取消或过期不提供普通新增入口。

地点详情已有导航与复制能力，见 [地点介绍](../src/components/features/location-detail/location-intro-card.tsx)。若在队伍卡增加导航，只能明确写“目的地导航”，不能把景点坐标冒充集合点；当前集合信息是自由文本，先用复制满足需要，不急于增加结构化地址和选点地图。

**日历限制：** 一次性导入不是自动同步；提示变更以队伍页为准，后续取消/改时不会天然更新已导入项目。不要为第一版引入日历账户授权、全量订阅或私密公开 feed。若引入含集合点的导出，需另评估导出后无法收回的隐私影响。

**验收：** 用户在一个屏幕区域内能回答“我是否加入、是否确定出发、什么时候、在哪里集合、怎么联系”；成员/非成员、未成团/成团/取消等状态均真实。日历另外检查跨日和不同时区，至少验证 Apple/Google 的实际导入结果，未完成不能声称兼容。确认收益需实际任务观察，不能从增加按钮直接推导爽约率下降。

### 3. 只通知会影响赴约的变化

借鉴 Luma 按变更影响发送通知的做法，先限定为已有参与关系中的事务信息：

- 取消活动、确认成团，以及可编辑范围内的出发时间/时长、集合信息变更；发送给当时仍有效的成员。公开地点/日期在当前编辑 UI 中受限，不因通知功能顺带开放改期/换地点。
- 保存前显示“将通知当前成员”；普通介绍润色不逐次通知。邮件写清变化、当前状态和队伍链接，避免携带成员联系方式；页面保留最新状态，即使邮件未送达也有权威信息。
- 优先建立关键变更投递闭环，再考虑一次出发前提醒。暂不复制 Luma 的提前 1 天和 1 小时双提醒，不新增通知中心、红点、站内聊天、群发编辑器。

这不是“现有 Resend 多调用一次”：活动保存成功与邮件投递失败是不同状态；需要持久记录待投递事件、按事件版本和收件人去重、有界重试及失败可见性。重复取消/更新不能重复刷邮件，退出成员不再收到后续行程提醒；Preview 仍不能发送生产通知。具体存储/任务方案应遵循 [可靠性规则](../CODING_STANDARDS.md#可靠性与性能设计)，本研究不预先批准新资源或数据库结构。

**验收：** 覆盖保存成功但投递失败、重复投递、快速连续修改、成员退出及取消后已排定提醒等情况。成功反馈区分“已保存”与通知状态，不虚报送达。活动取消后仍可从旧链接看到取消状态，不照搬 Luma 删除活动页面的做法。

## 暂不增加的能力

- 票务、支付、票种、候补和审批：当前小队直接加入流程没有需要这些能力的证据，审批还与已接受 ADR 冲突。
- 社区日历、订阅、CRM、签到核销、活动后问卷、营销群发：分别引入新的运营流程，不解决本次最明确的断点。
- 聊天、收藏、复杂行动本、个性化推荐：已经退出产品范围，不能借竞品调研恢复。
- 复制活动、模板库、富文本主题：可能帮助高频发起者，但尚无重复发起的真实频次证据。先观察是否确有重复录入负担。
- 重做首页、增加装饰动画或大面积改版：现有公开页面已完成多轮体验改造，本次问题集中在任务衔接和赴约信息。

## 如何验证取舍

先请少量首次使用者分别完成“从分享链接加入”“从地点发起并补联系方式”“次日回来查看集合与退出”三项任务，记录在哪里停住、是否重找目标/重填、能否正确解释加入与成团；同时让发起者演练一次取消。先形成基线，再在同样任务上比较，勿先设没有依据的转化提升百分比。

如果关键通知的实际使用场景尚未出现，保留设计记录即可；若发起者已反复手动通知或成员依赖旧信息赴约，再提升第 3 项的实施优先级。这里建议的是验证顺序，不声称已有访谈、漏斗或真实到场数据。

### 资料适用性与未验证项

- 创建帮助说明的是产品流程，不是“最少填写几项”的实测；本次不能据此量化 Luma 或 GoMate 的创建耗时。
- 报名、提醒与变更通知依据当前官方帮助；未验证各国家、客户端或账户的真实送达效果，也未验证 API/MCP 路径。
- “会更容易完成报名”“会减少爽约”等属于待验证假设。官方能力存在，不等于 GoMate 用户需要，也不证明采用后会产生同等收益。
